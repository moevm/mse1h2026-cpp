## Протокол встречи

- **Обсуждение итогов итерации 2**

    - в модуле сейчас придумано около 40 условий, но значительная часть из них сложная и тянет на высокий уровень сложности;
    - заказчик отметил, что студентам нужно давать больше практики, но без чрезмерного объема работы;
    - в качестве реалистичного ориентира предложено целиться примерно в 15–20 задач по модулю, а не пытаться внедрить все 40 условий;
    - при нехватке времени важнее, чтобы задачи были реализованы в коде, чем чтобы каждая из них была полностью интегрирована в Moodle;

- **Обсуждение объема работ**
    - основной фокус переносится на модуль тестирования;
    - необходимо равномерно двигаться и по отдельным задачам, и по лабораторным работам;
    - приоритет стоит сделать чуть больше на лабораторных работах, потому что они сложнее по реализации, чем отдельные задачи;
    - необходимо сделать хотя бы MVP лабораторных работ по тестированию;
    - по задачам тестирования нужно зафиксировать реалистичный объем, чтобы было понятно, чего ожидать к концу итерации;
    - общий ориентир по объему: реализовать 15–20 задач по модулю тестирования, при этом не стремиться закрыть весь первоначальный пул условий;
    - важно не переносить основную работу на май и распределить объем так, чтобы итерация была выполнима.

- **Формат вывода результатов тестирования**
    - заказчик уточнил идею, что студенты должны не получать готовую функцию красивого вывода, а постепенно реализовывать ее сами;
    - в начале модуля по тестированию нужно дать студентам задания на написание функций, которые формируют отчет о результатах тестирования;
    - такая функция должна выводить результаты в заранее заданном формате: номер теста, входные данные, ожидаемый результат, полученный результат, статус прохождения, общий процент пройденных тестов;
    - после реализации такой функции студент должен использовать ее в последующих заданиях модуля;
    - предлагается не делать одну чрезмерно универсальную функцию для всех возможных типов данных, если это слишком усложняет задание;
    - можно сделать несколько функций-шаблонизаторов для разных форматов данных, например:
        - одиночные значения;
        - одномерные массивы;
        - двумерные массивы;
        - строки;
    - смысл этой части модуля — показать студентам, что результаты тестирования нужно не просто получать, но и понятно анализировать;
    - нужно избежать ситуации, когда студент выводит неструктурированный набор значений вроде `1.0 1.0 0.0`, который невозможно нормально интерпретировать;
    - в перспективе можно иметь эталонную реализацию такой функции на стороне проверяющей системы, но выдавать готовый исходный код студентам необязательно.

- **Технические детали и уточнения по Moodle**
    - система должна поддерживать два основных режима работы:
        - генерация условия задания;
        - проверка студенческого решения;
    - при генерации используются номер задания, номер модуля/подмодуля и seed, после чего система выдает студенту условие;
    - при проверке используются тот же номер задания и тот же seed, чтобы проверялось именно то задание, которое было выдано студенту;
    - seed генерации и seed проверки должны совпадать;
    - в Moodle есть несколько основных полей: преднастройки задания, код проверки и описание задания;
    - в поле преднастроек задаются параметры запуска: номер задания, seed, режим работы и другие конфигурационные значения;
    - в описание задания нужно помещать результат вызова системы в режиме генерации условия, а также seed, который видит студент;
    - при проверке Moodle получает исходный код студента, передает его в проверяющую систему и получает результат проверки;
    - результат проверки может возвращаться в виде `fraction` от 0 до 1, либо в бинарном формате: 1 — верно, 0 — неверно;
    - дополнительный вывод проверки можно формировать через HTML-сообщение, например с таблицей «введено / ожидалось / получено»;
    - желательно предусмотреть режим или флаг предобработки текста задания в HTML-формат, чтобы не делать ручные замены `\n`, `\t` и других символов в коде Moodle;
    - интеграция с Moodle остается частично исследовательской задачей: нужно понять, на каком этапе корректно клонировать репозиторий и получать код проверяющей системы;
    - важно учитывать, что проверки в Moodle запускаются в изолированных docker-контейнерах, поэтому простое клонирование и сборка библиотеки в одной проверке не будет автоматически доступно в следующих проверках;
    - в примере с RISC-V курсом Python-модуль уже установлен в базовый docker-образ, поэтому он доступен во всех проверках; для текущей системы такого механизма пока нет.

- **Постановка требований**
    1) реализовать в коде реалистичный пул задач по модулю тестирования: ориентир 15–20 задач, без попытки закрыть весь первоначальный объем из примерно 40 условий;
    2) сделать MVP лабораторных работ по тестированию и уделить лабораторным работам больший приоритет, чем отдельным задачам;
    3) реализовать задачи и лабораторные в коде так, чтобы они могли работать через режим генерации условия и режим проверки решения;
    4) для задач, которые не успевают быть полностью заведены в Moodle, подготовить примеры интеграции и оставить реализацию в коде;
    5) оформить простую инструкцию по интеграции задач в Moodle в README или wiki: какие поля заполнять, как передавать seed, как вызывать генерацию и проверку, где смотреть результат;
    6) доработать формат вывода результатов тестирования: студенты должны сами реализовывать функции формирования отчета, которые затем используются в последующих заданиях;
    7) предусмотреть несколько вариантов функций вывода результатов для основных типов данных: одиночные значения, массивы и строки;
    8) на стороне проверяющей системы иметь эталонную логику проверки формата вывода результатов;
    9) уточнить и описать особенности запуска в Moodle с учетом изолированных docker-контейнеров и отсутствия предустановленного Python-модуля проекта в базовом образе;
    10) при возможности добавить флаг или режим вывода условия в HTML-формате для более удобной вставки задания в Moodle;
    11) к концу итерации отправить заказчику протокол и отдельное сообщение с указанием, куда смотреть и что проверять.
